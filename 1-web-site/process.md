# 進め方 — ゼロからページを作るまで

**この資料の他のファイルは「何が良いか」を書いている。ここは「どの順で決めるか」を書く。**

順番を間違えると、デザインをやり直すことになる。
やり直しの原因はほぼ**内容が決まる前に見た目を作り始めたこと**。

---

## 全体の順番

```
① 決める     誰に・何を・どうしてほしいか        ← ここが9割
② 集める     証拠・数字・言葉・写真
③ 組む       セクションの順序と中身（文章で）
④ 描く       レイアウト（ワイヤー）
⑤ 装う       ビジュアル
⑥ 作る       実装
⑦ 確かめる   検証
⑧ 出す       公開
⑨ 直す       計測して改善
```

**①〜③が終わるまで、④に進まない。** ここを飛ばすと、
「なんとなくかっこいいが、何も伝わらないページ」が完成する。

---

## ① 決める

これが埋まらないうちは何も作れない。**紙1枚で書けるまで削る。**

| 問い | 埋める内容 | 悪い例 |
|---|---|---|
| 誰に | 具体的な一人。役職・会社規模・状況 | 「中小企業の経営者」← 広すぎる |
| その人の何が困っているか | 本人の言葉で | 「DXが進んでいない」← 本人はそう言わない |
| どうなってほしいか | ページを見た後の**1つの行動** | 「認知度向上」← 行動ではない |
| なぜここなのか | 他ではない理由 | 「丁寧な対応」← 全社が言う |
| 何を証拠として出せるか | 数字・事例・顔・経歴 | （出せないなら、それも決定） |

### 「誰に」を絞る検査

書いた「誰に」から、**自社が扱えない相手を除外できているか。**
除外できていないなら、まだ絞れていない。

```
✕ 中小企業の経営者
○ 従業員20〜100名の製造業で、受発注をFAXと電話でやっていて、
  「何とかしたい」と思っているが何から手をつけるか分からない担当者
```

絞ると刺さる人が減ると思いがちだが、**逆。**
広く書くと誰にも刺さらない。

### 行動を1つに決める

CTA を複数持たせない（Hick の法則）。
「問い合わせ」「資料請求」「無料診断」を全部並べると、どれも選ばれない。

**主要行動を1つ決め、それ以外は明確に格を下げる。**

#### 行動の重さの階段

⚠️ 通し試作（F-3）で追加。「1つに絞れ」しか書いておらず、
**どういう行動なら重すぎないかの基準がなかった。**

**相手が背負うリスク（時間・情報・お金・社内での説明責任）の順に並べる。**

| 重さ | 行動 | 相手が背負うもの |
|---|---|---|
| 1 | 記事・事例を読む | なし（**行動ではない。CTAにしない**） |
| 2 | 更新情報を受け取る | メールアドレス |
| 3 | 資料をダウンロード | メールアドレス＋営業される予感 |
| 4 | **成果物を無料で受け取る** | 少しの情報。**見返りが先に来る** |
| 5 | 面談を予約する | 時間（30分〜）＋断る気まずさ |
| 6 | 無料トライアルを始める | 時間＋業務への組み込み |
| 7 | 申し込む・契約する | お金＋社内での説明責任 |

#### 選び方

- **実績がないほど、階段の下の方を主要行動にする。**
  実績ゼロの会社に 6〜7 を求められても、相手は判断材料がない
- **ただし 1〜3 は弱い。** 特に「資料DL」は行動として軽すぎて次に繋がりにくい
- **最も効くのは 4「成果物を無料で受け取る」**
  → 相手は自分が何を得るのかを**やる前に確認できる**
  → こちら側も「1件分の労力」で相手の本気度が分かる

```
✕ サービスに申し込む         ← 実績ゼロでは重すぎる
✕ 資料をダウンロード         ← 軽すぎて次に繋がらない
○ 見積を1件、無料で作らせてください   ← 成果物が先に手に入る
```

**選んだら、CTAの直下に「相手が何を差し出すか」を必ず書く。**
→ `hero-cta.md`「摩擦除去」

### 1ページか、複数ページか（ここで決める）

⚠️ 通し試作（F-7）で追加。どの工程にも判断がなかった。

| 条件 | 構成 |
|---|---|
| サービスが1つ・行動が1つ | **1ページ** |
| サービスが複数、または対象業種で説明が変わる | サービスごとに1ページ ＋ 会社トップ |
| 採用・IRなど別の読み手がいる | 別ページに分ける（**混ぜない**） |

**迷ったら1ページ。** ページを増やすと、更新が止まったページが必ず出る。

## ② 集める

**書き始める前に材料を集める。** 材料がないまま書くと抽象語で埋めてしまう。

集めるもの:

- [ ] **数字** — 削減時間、件数、期間、金額、対応社数。細かいほどよい
- [ ] **顧客の言葉** — 商談やヒアリングで実際に言われた表現。そのまま見出しに使える
- [ ] **実際の成果物** — 画面、レポート、納品物の写真
- [ ] **人** — 代表の顔写真、経歴、なぜこの事業をやるのか
- [ ] **よく聞かれる質問** — FAQ の中身になる
- [ ] **会社情報** — 所在地、設立年、代表者名

### 出せないものを確定させる

**「実績がない」「顔を出せない」も、決定として記録する。**
後で「ここに事例を入れよう」と手戻りしないため。

出せないなら、その分を**流れの透明性・具体的な数字・断れる安心感**で埋める設計にする。
→ `trust-btob.md`

### 集まらなかったときの代替材料

⚠️ 通し試作（F-4）で追加。**実際には半分は集まらない。**
「集めるもの」のリストだけがあって、集まらなかったときの進め方がなかった。

| 集まらないもの | 代わりに使えるもの |
|---|---|
| **顧客の声** | 商談で実際に聞かれた**質問**（FAQになる）／自分が現場で見た状況 |
| **導入企業のロゴ** | 対応できる業種・規模を具体的に書く（「造園・外構のみ」） |
| **削減時間の実測値** | **相手側の現状の数字**（「見積1件に2〜3時間」）。自社の成果でなくてよい |
| **事例** | **架空の事例を、架空と明記して**作る（サンプルレポート等）。隠さない |
| **実績年数** | 代表個人の経歴（会社の年数と人の年数は別） |
| **顔写真** | 経歴と「なぜこの事業をやるのか」の文章 |

**「相手側の現状の数字」は見落とされやすいが、実績ゼロでも書ける。**
「月20〜60時間を見積作成に使っている」は、自社の成果ではなく相手の状況の記述。
それでも十分に具体的で、自分ごと化に効く。

**それでも埋まらないなら、そのセクションを作らない。**
空のロゴウォールや匿名の「A社様」は、実績があるように見せる行為に近い（`0-core/ethics.md`）。

## ③ 組む（文章で）

**まだ絵を描かない。テキストエディタで書く。**

セクションの順序を決め、各セクションの見出しと本文を書く。
`structure.md` の標準順序を土台にする。

```markdown
# ヒーロー
見出し: 何から手をつけるべきか、無料で診断します
サブ: 現場の非効率を、外からの視点で言語化する。3分の入力から。
CTA: 無料診断を申し込む / 所要3分・費用はかかりません

# 課題（チェックリスト4項目）
- FAXと電話で受発注をしている → 転記のたびにミスが起き、確認の電話が増える
- 同じ数字を3か所に入力している → ...

# 解決策
...
```

### セクションごとに、何を書くか

⚠️ 通し試作（F-5）で追加。上のサンプルが Knacit の文言そのままで、
**別の題材に翻訳する手がかりがなかった。**

| セクション | 書くこと | 詳しくは |
|---|---|---|
| ヒーロー | 誰の何が・どうなるか。**10秒で分かる1文** | `hero-cta.md` |
| 軽い信頼 | 数字3つ。実績がなければ**対応範囲・経歴・返答速度** | `trust-btob.md` |
| 課題 | **状態**を4〜6個。解決策はまだ書かない | `layout-patterns.md` 2-A |
| 解決策 | 打ち手を3つ前後。**手順として**書く | `layout-patterns.md` 3-A |
| 流れ | 申し込んだ後に何が・いつ起きるか。**断れる地点を明示** | `trust-btob.md` |
| 料金 | 総額・何で変わるか・**最低契約期間**。隠さない | `0-core/ethics.md` |
| FAQ | ②で集めた**実際に聞かれた質問**。想定問答を作らない | `trust-btob.md` |
| 会社・人 | 誰がやるか。**出せないものは出せないと書く** | `trust-btob.md` |
| CTA | ①で決めた行動1つ。直下に摩擦除去の一言 | `hero-cta.md` |

### この段階で判断できること

- **文章だけで説得力があるか。** ここで弱いものは、デザインしても弱い
- セクションが多すぎないか（**目安は6〜9個** → `structure.md`）
- 順番が「頭の中の質問の順」になっているか → `structure.md`
- 抽象語が残っていないか → `ux-writing.md` の削る技術を通す

### 声に出して読む（と、その機械的な代替）

**人間は声に出して読む。** 詰まる箇所は、読み手も詰まる。

⚠️ 通し試作（F-8）で追加。**AIは声に出せない。** 代替手順がなかった。
声に出せない場合は、以下を機械的に通す。

```
□ 「することができます」「を行う」「させていただき」「となっております」を検索 → 0件
□ 一文が60字を超えていないか（超えたら句点で切る）
□ 同じ助詞が3語以内に連続していないか（「の」「が」の連続）
□ 同じ語尾が3文続いていないか（「〜ます。〜ます。〜ます。」）
□ 自社名を競合名に置換しても成立する文がないか
```

**これは代替であって、同等ではない。** 人間が読めるなら読む方が確実。

## ④ 描く（ワイヤー）

> ⚠️ **「描く」＝ゼロから絵を起こすことではない。**
> `layout-patterns.md` から**型を選んで並べる**ことがワイヤーである。
> （通し試作 F-9：④と `layout-patterns.md` の関係が不明瞭だった）

**白黒で、文字と箱だけ。** 色・写真・書体をまだ入れない。

- `layout-patterns.md` から各セクションの型を選ぶ ← **これが④の本体**
- **モバイル幅（375px）から描く。** デスクトップから描くと必ず入り切らなくなる
- 1画面に「一番目立つもの」が1つになっているか確認する

道具は何でもよい。紙、Figma、あるいは**HTMLを直接書いてもいい**
（`snippets/` の型を並べるだけでワイヤーになる）。

### ここで決めること

- セクションの型
- fold（スクロールなしで見える範囲）に何を入れるか
- CTA の位置（3箇所：ヒーロー / 中盤 / 最下部）
- 画像が入る場所と、そこに**実際に置ける画像があるか**

**「ここにいい感じの画像」で進めない。** 用意できないなら型を変える。

## ⑤ 装う（ビジュアル）

ここで初めて色・書体・写真を入れる。

**いきなり作らず、2段階に分ける。**
⚠️ 出典：[Anthropic `frontend-design` skill](https://github.com/anthropics/skills)（Apache-2.0）

### 第1段階：計画を書く（コードを書く前）

4項目だけの短い計画を、**文章で**書く。

| 項目 | 決めること |
|---|---|
| **Color** | 4〜6個の名前付き hex |
| **Type** | 2役以上（抑制的に使う特徴的な表示用書体 ＋ 本文用書体 ＋ 必要なら数値/キャプション用） |
| **Layout** | レイアウト構想。1文の説明と ASCII ワイヤーで比較する |
| **Signature** | **このページが記憶される、たった1つの要素** → 決め方は [visual-design.md §0](visual-design.md)。**ここには重複して書かない**（通し試作 F-13） |

### 第2段階：計画を批評してから作る

書いた計画を、**作り始める前に**自分で叩く。

> **同じような指示から、誰でも同じ結論に至りそうな部分はどこか。**

そこは「この案件のための選択」ではなく既定値なので、**変えて、何を変えたか書く。**
特に `visual-design.md` の「AIっぽさの3つのデフォルト」に該当していないか確認する。

計画が固まってから、**その計画どおりに**コードを書く。
色も書体も、すべて計画から導く。途中で思いつきを足さない。

### そのあとの手順

1. 1セクションだけ仕上げる ← **全部を同時に進めない**
2. そのセクションを基準に、残りを揃える

**最初に仕上げるのはヒーロー。** 一番難しく、一番効く。

### 実装時の注意

CSS のセレクタ詳細度に気をつける。
`.section` のような型ベースのクラスと、要素ベースのセレクタが**打ち消し合う**事故が起きやすい
（特にセクション間の margin / padding）。→ 実例は `LESSONS.md` L-001 / L-002

### 最後に1つ外す

> 出かける前に鏡を見て、アクセサリーを1つ外す（ココ・シャネル）

**大胆さは1箇所に集中させる。** シグネチャー以外は静かにする。
ブリーフに奉仕しない装飾は削る。

### 1セクション先行の理由

全セクションを50%ずつ進めると、**判断基準が定まらないまま量が増える。**
1つを100%にすると、それが基準になって残りが速い。

最初に仕上げるのは**ヒーロー**がよい。一番難しく、一番効くから。

## ⑦ 確かめる

`launch-checklist.md` を上から通す。特に:

- 320px で横スクロールが出ないか

### 実例と位置を比べる

⚠️ 通し試作で判明した最重要の問題（`trials/2026-08-01-zoen/LOG.md`）。

**この資料どおりに作ると、実例より系統的に「短く・薄く・大人しい」ページになる。**

| 指標 | 資料どおりに作った試作 | 実例(n=5) |
|---|---|---|
| ページ長 | 5.5画面 | 11.7〜16.4 |
| 情報密度 | 230字/画面 | 244〜561 |
| ボタン数 | 3 | 3〜47 |
| 角丸の種類 | 2 | 3〜10 |

偶然ではない。「余白を広く」「色数を絞る」「導線を1つに」が
**すべて同じ方向に効いて積み上がる。**

**だから、作り終えたら測って位置を確認する。**

```js
// snippets/js/metrics.js を読み込んで
uiuxMetrics();
// → references/metrics/ の実測値と比べる
```

判定の仕方（`references/metrics/` の注意書きと同じ）：

- **中央値に合わせにいかない。** 平均的なものが出来上がるだけ
- **外れているのが「意図」か「事故」かを区別する**
- 大半の軸は範囲内に収め、**1つの軸だけ意図して外す**（＝Signature）

> ⚠️ 実例の数値は現在 n=5 で、**基準として使える精度がない。**
> 「明らかに外れている軸がないか」を見る程度にとどめる。

## よくある失敗と、その原因

| 失敗 | 本当の原因 | 戻るべき工程 |
|---|---|---|
| 何を伝えたいか分からないページになった | ①で「誰に」が広すぎた | ① |
| 抽象的な言葉ばかりになった | ②の材料集めを飛ばした | ② |
| デザインを何度もやり直した | ③を飛ばして④から始めた | ③ |
| モバイルで崩れた | ④をデスクトップから描いた | ④ |
| 全体の統一感がない | ⑤で全セクションを同時進行した | ⑤ |
| 公開後に何をすればいいか分からない | ①で行動を1つに決めていない | ① |

**やり直しが発生したら、必ずどこかの工程を飛ばしている。**
その場で直さず、飛ばした工程に戻る。

## 規模別の目安

| 規模 | ①〜③ | ④〜⑤ | ⑥〜⑧ |
|---|---|---|---|
| 1ページのLP | ここに一番時間をかける | 型を選ぶだけ | 実装は速い |
| コーポレート（5〜10ページ） | ページごとに①を書く | 共通トークンを先に確定 | テンプレ化する |

**どの規模でも、①〜③に半分以上の時間を使うのが正しい。**
見た目を作っている時間が長いなら、たぶん①が甘い。
