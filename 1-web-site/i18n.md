# 日英バイリンガル

日本の BtoB サイトで英語を併記する場面は多い。
ただし**方式の選び方で、SEO と保守性が大きく変わる**。ここを最初に決める。

---

## まず「なぜ英語を出すのか」を決める

目的によって、必要な方式が変わる。

| 目的 | 必要な範囲 | 方式 |
|---|---|---|
| 見た目・雰囲気（国際感） | **英語は要らない。** 日本語のタイポで作れる | — |
| 海外からの問い合わせが実際にある | 全ページ | 別URL |
| 海外の人に会社を説明できればよい | 1ページだけ英語版 | 別URL（1枚） |
| 日本人だが英語表記を好む層がいる | 主要ページ | 切替式でも可 |

**「なんとなく国際的に見えるから」で全ページ二言語化すると、
保守が2倍になり、SEO も弱くなる。** 目的がないなら英語は出さない方がよい。

---

## 方式は2つ

### A. 別URL方式（`/en/` を分ける）★SEO的に正しい

```
https://example.com/          日本語
https://example.com/en/       英語
```

**メリット**
- 検索エンジンが**言語ごとに別ページとして正しく認識する**
- 英語で検索した人に英語ページが出る
- ページ内に1言語しかないので、翻訳ツール・スクリーンリーダーが正しく動く

**デメリット**
- ページ数が2倍。更新漏れが起きる
- 実装コストが高い

**実装**
```html
<!-- 日本語ページの <head> -->
<link rel="alternate" hreflang="ja" href="https://example.com/">
<link rel="alternate" hreflang="en" href="https://example.com/en/">
<link rel="alternate" hreflang="x-default" href="https://example.com/">
```

`hreflang` は**両方のページに、両方向を書く**（片方だけだと無効）。
`x-default` は、どの言語にも当てはまらない場合の既定。

### B. 切替式（同一ページ内で表示を切り替える）

```html
<p><span class="ja">無料で診断します</span><span class="en">Free diagnosis</span></p>
```

**メリット**
- ページが1つ。更新漏れが起きない
- 実装が軽い（`snippets/js/lang-toggle.js`）
- 訳の対応関係が目で見て分かる

**デメリット（重要）**
- **HTML に両言語が同時に存在する。** 検索エンジンは1ページを1言語として扱おうとするため、
  混在は正しく評価されない。`hreflang` も使えない
- 非表示側のテキストも DOM に存在する → スクリーンリーダーの実装によっては読まれうる
- **翻訳の量が増えるほど HTML が肥大する**

**結論：切替式は「英語がおまけ」の場合に限る。**
英語圏からの集客を狙うなら A を選ぶ。

---

## 切替式を使うときの最低条件

`snippets/js/lang-toggle.js` の実装で満たしていること。

- [ ] **`<html lang>` を実際に書き換える**（読み上げ言語が変わる）
- [ ] `localStorage` に保存して、次回訪問でも維持する
- [ ] トグルボタンに `aria-pressed` と `aria-label`
- [ ] **JS が動かなくても日本語は読める**（既定を `ja` にする）
- [ ] 非表示は `display: none`（`visibility: hidden` だと領域が残る）
- [ ] 切り替え時にレイアウトが飛ばない

```css
[data-lang='ja'] .en { display: none; }
[data-lang='en'] .ja { display: none; }
```

> ⚠️ このCSSは**HTML側の `<style>` に先に書く**方がよい。
> JS から注入すると、一瞬だけ両言語が見えて CLS が発生する。

---

## レイアウトが崩れる原因

**英語は日本語より横に長くなる。** 同じ内容で 1.3〜2倍。

| 要素 | 起きること | 対処 |
|---|---|---|
| ボタン | 文字がはみ出す／2行になる | `min-width` ではなく `padding` で作る。高さを `min-h-*` で固定 |
| ナビ | 項目が入り切らない | 英語時は項目名を短縮する、または早めに `md` を上げる |
| 見出し | 行数が変わってレイアウトが動く | `min-height` を確保するか、行数変動を許容する設計にする |
| 表の見出し | 列幅が崩れる | 列幅を明示する |

**確認方法：英語に切り替えた状態で、320px 幅にする。** ここが一番崩れる。

## 翻訳の質

### 直訳しない

日本語の丁寧表現をそのまま英語にすると、不自然で回りくどくなる。

| 日本語 | ✕ 直訳 | ○ 自然な英語 |
|---|---|---|
| お気軽にお問い合わせください | Please feel free to contact us casually | Get in touch |
| 無料診断を申し込む | Apply for free diagnosis | Request a free check |
| 弊社では〜させていただいております | We are humbly providing... | We help you... |

**英語は日本語より短く、直接的に書く。**
`ux-writing.md` の「削る技術」は英語でも同じ。

### 訳さないもの

- **ブランド名・製品名** — `translate="no"` を付ける
- 日本固有の制度・肩書き — 訳すと誤解される。ローマ字＋補足にする

```html
<span translate="no">Knacit</span>
```

### 訳の管理

切替式で `.ja` / `.en` を並べると、**片方だけ更新して食い違う**事故が起きる。

- 日本語を直したら、必ず同じコミットで英語も直す
- 訳が未完成なら、**英語版を出さない**（中途半端な英語は信頼を下げる）

## 数値・日付・通貨

**ハードコードしない。**

```js
// ✕
const d = '2026年7月31日';

// ○
new Intl.DateTimeFormat(lang, { dateStyle: 'long' }).format(date);
new Intl.NumberFormat(lang, { style: 'currency', currency: 'JPY' }).format(20000);
```

| 項目 | 日本語 | 英語 |
|---|---|---|
| 日付 | 2026年7月31日 | July 31, 2026 |
| 金額 | ￥20,000 | ¥20,000 / JPY 20,000 |
| 電話 | 090-1234-5678 | +81 90-1234-5678 |

**言語判定を IP アドレスでやらない**（Google の推奨に反する。VPN・旅行者で誤判定する）。
`Accept-Language` ヘッダか、ユーザーの明示的な選択を使う。

---

## フォント

欧文フォントを**先に**書く（`0-core/typography.md`）。

```css
font-family: 'Inter', 'Zen Kaku Gothic New', sans-serif;
```

英語表示時に日本語フォントの従属欧文が使われると、途端に素人っぽくなる。

**英語表記は米綴りに統一する**（center / organization / -ize）。
混在すると気づかれる。

## 判断の早見表

```
英語からの集客を狙う？
├─ はい → 別URL（/en/）＋ hreflang。全ページ訳す覚悟がいる
└─ いいえ
   ├─ 会社説明だけ英語で必要 → /en/ に1ページだけ作る
   ├─ 雰囲気として少し英語を出したい → 切替式（.ja/.en）
   └─ 特に理由がない → 英語を出さない
```

**迷ったら出さない。** 中途半端な二言語は、保守コストだけ増えて誰も読まない。
