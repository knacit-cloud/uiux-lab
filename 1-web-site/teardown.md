# ティアダウン — 良いサイトを分解して学ぶ

**「このサイトいいな」で止めると、何も残らない。**
なぜ良いのかを言葉にして初めて、自分の手札になる。

ここはその**分解の型**。溜まった観察は `teardowns/` に置く（着手時に作る）。

---

## なぜ型が要るか

型なしで見ると、**目立つ部分（配色・アニメーション）にしか目が行かない。**
実際に効いているのは、余白・順序・言葉といった地味な部分であることが多い。

順番を固定すると、そこを見落とさない。

---

## 分解の順番

**上から順に見る。ビジュアルは最後。**

```
① 誰に何を売っているか       ← 見た目より先に、これを当てる
② セクションの順序
③ fold に何を置いたか
④ CTA の設計
⑤ 信頼のつくり方
⑥ 言葉づかい
⑦ レイアウトの型
⑧ ビジュアル
⑨ 実装（DevTools）
⑩ 盗めるもの / 盗まないもの
```

---

## 見るときのコツ

### ① まず10秒で閉じる

**ページを開いて10秒で閉じ、何が分かったかを書く。**
これが本物のファーストインプレッション。じっくり読んだ後では二度と得られない。

「何の会社か分からなかった」なら、そのサイトはそこが弱い。

### ② スマホで見る

多くのサイトはデスクトップで作られ、スマホで崩れている。
**流入の大半はスマホ**なので、そちらが本番。

### ③ 数える

主観を避けるには数える。

- 色は何色使っているか
- 書体は何種類か
- CTA は何個あるか
- セクション上下の余白は何px（DevTools で測る）
- 本文の行間はいくつか

**「なんとなく余白が広い」ではなく「上下 112px」と記録する。**
数字は自分の実装にそのまま持ち込める。

### ④ DevTools で測る

```js
// 本文の行間と文字サイズ
const p = document.querySelector('p');
getComputedStyle(p).fontSize + ' / ' + getComputedStyle(p).lineHeight

// セクションの余白
getComputedStyle(document.querySelector('section')).paddingTop

// 使われている色を数える
[...new Set([...document.querySelectorAll('*')]
  .map(e => getComputedStyle(e).color))].length
```

### ⑤ 悪い例も記録する

**良いサイトだけ見ていると、なぜそれが良いか分からない。**
「ここが読みにくい」「何の会社か分からない」も同じ型で記録する。

`visual-design.md` の「安っぽさの10症状」を照らし合わせると言語化しやすい。

## 盗む / 盗まない の判断

**そのまま真似してよいのは「構造」まで。「表現」は真似しない。**

| 盗んでよい | 盗んではいけない |
|---|---|
| セクションの順序 | キャッチコピーの文言 |
| CTA の配置と数 | ロゴ・イラスト・写真 |
| 余白・行間の数値 | 独自のイラストレーション表現 |
| フォームの項目構成 | **背負えない実績の見せ方** |
| 情報の粒度 | 文章そのもの |

### 特に注意

**「実績が豊富な会社の見せ方」を、実績のない会社が真似すると破綻する。**
ロゴウォールが空、事例が匿名、数字が丸い — それは真似ではなく劣化コピーになる。

自分が出せる材料で成立する構成を選ぶ（`trust-btob.md`）。

### 著作権

デザインの**アイデア・レイアウト構造**は保護されないが、
**文章・画像・イラストは著作物**。コピーしない。
記録に引用するときは短く、出典URLを添える。

## どこを見るか（探し方）

- **自分の業界の競合** — 一番実用的。何を出していて何を出していないか
- **自分が申し込みたくなったサイト** — 実際に行動した体験は情報量が多い
- **海外の BtoB SaaS** — 情報設計が洗練されている。ただし**そのまま日本のBtoBに持ち込まない**
  （日本の商習慣では、会社情報・顔・電話番号の重みが違う）
- **公的機関のサイト** — アクセシビリティの参考になる

**ギャラリーサイトで「かっこいいデザイン」を集めるのは、優先度が低い。**
コンバージョンの文脈がない見た目だけを見ても、判断力は育たない。

## 溜め方

```
teardowns/
├─ 2026-08-01-example-corp.md
├─ 2026-08-15-example-saas.md
└─ README.md   ← 横断して気づいたパターンをまとめる
```

**5件ぐらい溜まると、共通パターンが見えてくる。**
そのとき `README.md` に「この業種のLPはだいたいこうなっている」と書く。
それが、次に作るときの一番速い出発点になる。

型に当てはまらない発見は `LESSONS.md` ではなくここに書く
（`LESSONS.md` は自分で作って踏んだ不具合の記録）。
