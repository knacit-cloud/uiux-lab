# 2-web-app — 扱う範囲

> ✅ **SCOPE 確定（2026-08-08）。** 中身はこれから埋める。
> ここに書いた境界・前提から外れることを、このフォルダに書かない。

## 対象

**毎日使う、操作するための画面。**

- ダッシュボード
- 管理画面 / 業務システム
- SaaS のログイン後画面
- 内製ツール

## この対象の前提（`1-web-site` との決定的な違い）

| | LP・サイト | Web アプリ |
|---|---|---|
| ユーザー | 初めて来た他人 | **習熟していく同じ人** |
| 滞在 | 数十秒 | 数時間／毎日 |
| 離脱 | 1クリックで消える | **離脱できない**（業務だから） |
| 学習 | 期待できない | **期待できる**（ショートカット等が生きる） |
| 余白 | 広いほど良い | **広すぎると苦痛**（情報密度が価値） |
| 選択肢 | 絞る | **絞りすぎると回り道が増える** |
| 目的 | コンバージョン | **タスク完了までの時間と失敗率** |
| 成功指標 | 離脱率・CV率 | 作業時間・エラー率・サポート問い合わせ数 |

**この表が「混ぜない」理由そのもの。**
LP の作法（広い余白、大きなヒーロー、選択肢を1つに絞る）を管理画面に持ち込むと、
毎日使う人にとって苦痛な画面になる。

---

## 境界（どちらに置くか迷う5つ）

| 画面 | 置き場所 | 理由 |
|---|---|---|
| ログイン画面 | **`2-web-app`** | 毎日通る。指標が「失敗率」であってCV率ではない |
| サインアップへの導線・訴求 | `1-web-site` | まだ他人。信用を作る話 |
| 初回オンボーディング | **`2-web-app`** | 空状態の設計と不可分 |
| 設定画面 | **`2-web-app`** | フォームと権限の話 |
| 課金・プラン変更 | **`2-web-app`**（料金**表**は `1-web-site`） | 変更操作は破壊的操作の作法 |
| アプリ内通知 | **`2-web-app`** | トースト・バナーと同じ枠 |

## ここに入れないもの

- LP のヒーロー、CTA、コンバージョン設計 → `1-web-site/`
- 料金**表**（未契約者に見せる比較表） → `1-web-site/`
- タッチジェスチャ、OS固有の作法 → `3-mobile/`
- コントラスト・タイポ・余白の数値基準 → `0-core/`

## 実例をどう観察するか（`1-web-site` と同じやり方は使えない）

**業務アプリの本番画面はログインの向こう側にある。**
`1-web-site` では実例をブラウザで開いて `metrics.js` で実測できたが、それができない。
これはこのフォルダ最大の制約であり、**先に認めておく。**

### 今回とる方法：ログイン不要で実測できるものに限定する

観察対象の候補（**🔍 リンクのみ・実在と実測可否は未確認。着手時に1つずつ確かめる**）：

| 候補 | 種別 | 狙い |
|---|---|---|
| Shopify Polaris | 公式デザインシステム | コンポーネントが動く形で公開されている想定 |
| Atlassian Design System | 公式デザインシステム | 業務システム寄りの作法 |
| IBM Carbon | 公式デザインシステム | データ密度の高い画面 |
| Material Design 3 | 公式ガイドライン | 一次資料としての基準値 |
| デジタル庁 デザインシステム | 公式・**日本語** | 日本語での密度・行間の実際 |
| SmartHR Design System | 公式・**日本のBtoB** | 日本の業務システムの実際 |
| Grafana Play | **ログイン不要の実ダッシュボード** | 本物の業務画面に最も近い |

**日本のものを必ず2つ以上入れる。**
`1-web-site` で「導線を絞る」が海外SaaS寄りだった疑い（linear 3ボタン vs kaminashi 47）が出ている。
同じ偏りを繰り返さない。

### この方法の限界（資料に明記して回る）

公式デザインシステムのサンプルは**理想形であって、実際の業務画面ではない**。
実データが入って項目が増え、権限で分岐し、例外が生えた後の姿は測れていない。
**「公式DSでこうなっていた」と「現場でこうなっている」を混同して書かない。**

## 何を測るか（`metrics.js` の流用可否）

`metrics.js` の測定項目は LP 用に作られている。そのまま持ち込めない。

| 項目 | 流用 | 理由 |
|---|---|---|
| 本文サイズ / 行間 / 1行の文字数 | ✅ そのまま | `0-core` 由来。対象に依らない |
| 書体数 / 文字色・背景色の種類数 | ✅ そのまま | 一貫性の指標として同じ |
| 角丸の最頻値・種類数 / 影の種類数 | ✅ そのまま | LPとの**比較**に意味がある |
| セクション余白 / コンテナ幅 | △ 読み替え | アプリは「セクション」でなく「領域」 |
| fold内のボタン数 / fold内にh1 | ❌ 使わない | fold はLP固有の概念 |
| ページ長（画面数） | ❌ 使わない | アプリは縦に長くない |
| 密度（字/画面） | △ 定義を変える | 字数でなく**情報要素数**で測るべき |
| ボタン数 | △ 読み替え | 「同時に見えるアクション数」に変える |

### アプリ用に新しく要る指標（`metrics.js` に追加する）

- **1画面に収まる行数**（テーブルの可視行数）
- **行の高さ**（row height）
- **余白の最小単位**（LPの8pxより小さい可能性がある）
- **サイドバーの項目数**と階層の深さ
- **同時に見えるアクション数**
- **主要操作までのクリック数** ← 機械では測れない。**人間が数える（検証の層③）**

## 実装の前提

- **資料本文はフレームワーク非依存で書く。** React / Vue / Svelte のどれでも通る書き方
- **`snippets/` はバニラ HTML + Tailwind CDN で1ファイル完結**（`1-web-site` と同じ）。
  ビルド不要で即開ける＝実測できる、という既存の利点を捨てない
- 状態（ローディング・空・エラー・undo・フォーカストラップ）は**少量のバニラJS**で表現する
- **静的HTMLで表現しきれない部分は、資料に「実装依存」と書く。**
  書けたふりをしない

## ここに入れる予定のもの（着手順）

### 先に埋める3つ

1. **`density.md` — 情報密度と余白**
   どこまで詰めていいか。LPの「余白は広いほど良い」がどこで反転するか。
   density 切り替え（compact / comfortable）。`0-core/color-spacing.md` との接続点
2. **`states.md` — 状態の設計**
   ローディング（スケルトン vs スピナー）、空状態、エラー状態、部分失敗、楽観的更新
3. **`data-table.md` — データテーブル**
   列設計、ソート、固定列、行選択、一括操作、ページネーション vs 無限スクロール

### その後

- **フィルタと検索**：ファセット、保存済みフィルタ、URL への状態反映
- **フォーム（アプリ内）**：インライン編集、自動保存、競合の扱い
- **ナビゲーション**：サイドバー、階層、パンくず、タブ、コマンドパレット
- **通知とフィードバック**：トースト、バナー、確認ダイアログ、undo
- **破壊的操作**：確認の作法、undo 猶予、ソフトデリート
- **権限とロール**による表示差分
- **キーボード操作**：ショートカット、フォーカス管理、モーダルのフォーカストラップ
- **大量データ**：仮想化、遅延読み込み
- **ログイン・オンボーディング**：失敗率で設計する
- **現代的な Web アプリの実装傾向**（Linear / Vercel / Notion 系が何をしているか、なぜか）
