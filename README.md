# uiux-lab

Web デザインと UI/UX の参考資料。**次に何かを作るときの土台**として使う。

人間が読む資料であると同時に、**Claude Code などの AI に読ませる指示書**でもある。
新しいサイト／アプリを作るとき「`uiux-lab` を参照して作って」と言えば、毎回同じ基準で出せる状態を目指す。

---

## 一番大事なルール：対象を混ぜない

LP に必要なものと、管理画面に必要なものと、ネイティブアプリに必要なものは違う。
**同じ引き出しに入れると全部が鈍る。** だから対象ごとにフォルダを分け、
各フォルダの先頭に `SCOPE.md`（扱うもの／扱わないもの）を必ず置く。

資料を追記するときは、まず「これはどの対象の話か」を決めてから書く。
どこにも入らないなら、それは `0-core`（全対象共通）か、まだ書くべきでないかのどちらか。

## 構成

| ディレクトリ | 対象 | 状態 |
|---|---|---|
| `0-core/` | 全対象で共通する土台。原則・アクセシビリティ・タイポ・色・余白 | ✅ 実装済み |
| `1-web-site/` | LP・コーポレートサイト（読ませて行動させるページ） | ✅ 実装済み |
| `2-web-app/` | ダッシュボード・管理画面（操作させる画面） | 🔲 SCOPE のみ |
| `3-mobile/` | ネイティブアプリ（iOS / Android） | 🔲 SCOPE のみ |
| `references/` | 出典台帳。一次資料へのリンクと検証状態 | ✅ 実装済み |
| `snippets/` | コピペして動く実装（CSS / JS / HTML）＋見本帳 | ✅ 実装済み |
| [`LESSONS.md`](LESSONS.md) | **実際に作って踏んだ不具合の記録。** 追記していく | ✅ 運用中 |
| [`ANTI-PATTERNS.md`](ANTI-PATTERNS.md) | **やってはいけないことの逆引き索引。** 症状 → 原因 → 該当ファイル | ✅ 実装済み |

3つの役割分担：

| ファイル | 役割 | いつ読むか |
|---|---|---|
| `0-core/` `1-web-site/` | **こうすべき** | 作る前・作りながら |
| [`ANTI-PATTERNS.md`](ANTI-PATTERNS.md) | **こうしてはいけない**（症状から引く） | 「なんか変」と思ったとき |
| [`LESSONS.md`](LESSONS.md) | **こう書いたらこうハマった**（実測つき） | 同じ失敗を繰り返さないため |

**「べき論」だけだと劣化する。** 実際に踏んだ記録と、症状からの逆引きが要る。

### すぐ動かす

```bash
node .claude/server.js
```

→ http://localhost:4322/snippets/ が**ライブカタログ**。
`1-web-site/layout-patterns.md` のセクション型が実際に動く状態で並んでいる。
詳細は [snippets/README.md](snippets/README.md)。

`0-core` は**薄く保つ**。「本当に全対象で成り立つことだけ」を入れる。
迷ったら対象フォルダ側に書く。core が太ると混在が始まる。

## 使い方

### 人間として使う
作るものが決まったら、`0-core/` → 該当する対象フォルダ、の順に読む。

### AI に使わせる
プロジェクト側で参照させる。例：

```
~/Desktop/uiux-lab/AGENTS.md と 0-core/ と 1-web-site/ を読んでから、
このLPのヒーローセクションを設計して
```

`AGENTS.md` がルール本体。まずそれを読ませる。

## 出典の扱い

この資料の主張には出典をつける。検証状態は `references/sources.md` の記号ルールに従う。

- **⚠️** AI が本文を照合済み・人間未確認
- **✅** 人間が確認済み
- **🔍** リンクのみ。本文未照合

`✅` を付けられるのは人間だけ。AI は照合しても `⚠️` 止まり。
