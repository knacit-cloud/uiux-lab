# intake — 「作りたい」を受け取ったときの受付

> ⚠️ 2026-11-20 作成。AI が公開資料（`sources.md` #26〜#35）を元に組んだもの。実際の依頼で回すまで仮。

**このフォルダの役割：作り始める前に、決まっていない項目を見つけて聞き返す。**

AI は足りない情報があっても、聞かずに仮定して進む傾向が強い（#31）。
仮定で埋まった部分は「よくある平均値」になる。それが AI っぽさの正体（`ai-bias-check.md`）。
だから、**作る前に「平均値で埋まりそうな項目」を潰す。**

## SCOPE

| 入れるもの | 入れないもの |
|---|---|
| 依頼を受けてから作り始めるまでの手順 | 作り方そのもの（→ `0-core` 〜 `3-mobile`） |
| 聞くべき項目と、聞き方 | ブランドの決め方の詳細（→ `4-brand`） |
| AI の偏りの点検表 | 見本の渡し方の詳細（→ `references/input-methods.md`） |
| 返答の型 | |

## ファイル

| ファイル | 中身 | いつ使う |
|---|---|---|
| `README.md`（これ） | 全体の流れと**返答の型** | 依頼を受けたら最初に |
| `items.md` | 聞く項目の一覧。項目ごとに「AI が勝手に入れる値」と「聞き方」 | 足りない項目を探すとき |
| `screenshot-reading.md` | スクショから**読めること／読めないこと** | スクショが来たとき |
| `ai-bias-check.md` | AI が偏りやすい点の点検表 | 作る前の計画と、作った後の確認で2回 |
| `BRIEF.template.md` | 受付の結果をまとめる1枚 | 質問が終わったら |

## 流れ（7段階）

```
① 受け取る      依頼文・スクショ・URL・既存ファイルを全部見る
② 自分で埋める  聞く前に、渡されたものと既存リポジトリから分かる項目を埋める
③ 聞く          埋まらない項目のうち、結果を一番変えるものだけ聞く（1回5問まで）
④ 復唱する      BRIEF にまとめて見せる。「これで作ります」
⑤ 承認          本人が OK するまで作らない
⑥ 作る          作る前と作った後に ai-bias-check を当てる
⑦ 見比べる      自分でスクショして見本・BRIEF と照合（input-methods.md の自己検証ループ）
```

### ② 自分で埋める（聞く前に）

**分かることを聞かない。** 聞く前に、作業ディレクトリと渡されたものから自分で答えを探す（#29）。

- プロダクトに `DESIGN.md` があるか → あればブランド系の質問は全部飛ばす
- 既存のコードがあるか → 技術スタックは聞かない
- スクショから読めることは読む（`screenshot-reading.md`）
- 過去の BRIEF があるか

### ③ 聞く — 聞き方のルール

1. **1回に5問まで。** 一番小さい質問の組で、残りの作業が進められるようにする（#28）
2. **順番は「間違えたときのやり直しが大きい順」。** 対象（サイトかアプリか）→ 誰に → 何をしてほしいか → ブランド → 見た目の細部
3. **全部に選択肢をつける。** 自由記述だけで聞かない。答えるのが楽になる
4. **全部に「わからない場合の既定値」をつける。** 本人が決められなくても止まらない。ただしその既定値は**この資料の既定値**であって、AI の平均値ではない
5. **既定値で進めた項目は BRIEF に「仮」と書く。** 後で戻れるように
6. **2周目は「前の答えで新しく出た穴」だけ聞く。** 同じことを2回聞かない

## 返答の型

### 型A：文章だけで「〇〇を作りたい」と来たとき

```
作る前に、結果を大きく変える点を確認させてください。
（分からないものは「わからない」で大丈夫です。その場合は右の既定値で進めます）

1. 何を作りますか？
   → [LP・会社サイト / 管理画面・業務ツール / スマホアプリ]
   わからない場合：〈依頼文から推定した対象〉
2. 誰が見ますか？ 具体的な1人で教えてください（役職・会社の規模・困っていること）
   わからない場合：聞かずに進めない。ここだけは必須
3. 見た人に、最後に何をしてほしいですか？（1つ）
   → [問い合わせ / 資料請求 / 購入 / 登録 / 毎日の作業を終える]
4. 色やロゴは決まっていますか？
   → [DESIGN.md がある / ロゴと色だけある / 何もない]
   わからない場合：4-brand の手順で、最初に3案出します
5. 使える写真はありますか？
   → [実物の写真がある / ない（イラスト・図で作る）]
   わからない場合：写真なしで作る。ストック写真は使わない

（すでに分かっている点：〈②で自分で埋めた項目〉）
```

### 型B：スクショが来たとき

`screenshot-reading.md` の型を使う。要点：

```
このスクショから読めたこと：
- 構成：〈〉
- 密度：〈〉
- 色の傾向：〈推定。正確な値ではない〉

読めなかったこと（ここを決めないと、AI の平均値で埋まります）：
1. このスクショの「どこ」を取り入れたいですか？
   → [全体の雰囲気 / 並べ方 / 色 / 文字の組み方 / 特定の部品（どれか指してください）]
2. 逆に、真似したくない部分はありますか？
3. ……
```

### 型C：「いい感じに」「おまかせで」と来たとき

**おまかせでも、②と「誰に」だけは止めて聞く。** それ以外は既定値で進め、
BRIEF の該当欄を全部「仮」にして、**3案を出して選んでもらう**形にする。
1案だけ出すと、それが AI の平均値でも比べる相手がない。

### 型D：答えが返ってきたとき

1. 答えを BRIEF に反映
2. その答えで**新しく出た穴**があるか確認（例：「アプリ」と答えた → iOS か Android か、が新しい穴）
3. 穴がなければ BRIEF を全文見せて「これで作ります。違う所はありますか？」
4. 穴があれば、その分だけ聞く（型A の形で）

### 型E：作ったものを見せるとき

```
作りました。BRIEF のどの項目をどう反映したか：
- 〈項目〉→〈どうしたか〉
AI の偏り点検（ai-bias-check.md）で引っかかったもの：
- 〈あれば。意図して残したものは理由つき〉
見本と並べて分かったズレ：
- 〈3つまで。直したもの／残したもの〉
```

## この仕組み自体を育てる

- 聞かずに作って外した → `LESSONS.md` に記録し、その項目を `items.md` で優先度を上げる
- 毎回聞いているのに毎回同じ答え → 既定値に昇格させて、聞くのをやめる
- 新しい偏りを見つけた → `ai-bias-check.md` に足す。**出典がない観察は「独自」と明記**
