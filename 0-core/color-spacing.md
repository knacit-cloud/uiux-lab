# 色と余白

見た目の「素人っぽさ」の大半は、色数の多さと余白の不揃いから来る。
センスの問題ではなく**ルールを決めていない**問題。

---

## 色

### 色数を絞る

必要なのはこれだけ。

| 役割 | 数 | 用途 |
|---|---|---|
| **Neutral（グレー系）** | 8–10段階 | 画面の9割。背景・境界線・文字 |
| **Primary（ブランド色）** | 5–7段階 | 主要アクション、強調。**使う面積は小さい** |
| **Semantic** | 各3段階 | success / warning / error / info |
| Accent | 0–1色 | 本当に必要なときだけ |

**よくある失敗：ブランド色を大面積に使う。**
ブランド色は「ここを見て」の合図。全面に敷くと合図として機能しなくなる。
背景はニュートラル、ブランド色は CTA と強調に限定する。

### 段階の作り方

1色につき 50 / 100 / 200 … 900 のように段階を持つ。用途を固定する。

| 段階 | 用途 |
|---|---|
| 50–100 | 淡い背景（選択状態、注意喚起の帯） |
| 200–300 | 境界線、区切り |
| 400–500 | アイコン、補助テキスト |
| 600–700 | **主要アクションの背景、本文リンク** |
| 800–900 | 見出し、本文の文字色 |

**本文の文字色に純黒 `#000` を使わない。** 白背景とのコントラストが強すぎて目が疲れる。
`#1a1a1a`〜`#2e2a26` あたりの、わずかに色味を含んだ濃色を使う。
同様に背景の純白 `#fff` も、少し灰か暖色に寄せると紙に近くなる。

### トークンで持つ

hex を HTML/JSX に直書きしない。**必ず変数経由。**

```css
:root {
  /* 原子トークン：色そのもの */
  --color-neutral-900: #2e2a26;
  --color-primary-600: #a9786f;

  /* 意味トークン：用途で名付ける ← 実際に使うのはこっち */
  --text-primary:   var(--color-neutral-900);
  --text-muted:     var(--color-neutral-500);
  --bg-surface:     var(--color-neutral-50);
  --border-default: var(--color-neutral-200);
  --action-primary: var(--color-primary-600);
}
```

意味トークンを挟むと、**ダークモードとブランド変更が変数の差し替えだけで済む。**
`--color-primary-600` を直接使い回すと、後から全箇所を直すことになる。

### コントラストは設計時に確認する

- 通常テキスト **4.5:1**、大きい文字・UI部品 **3:1**（詳細は `accessibility.md`）
- **ホバー・フォーカス状態はコントラストを上げる方向に変える。** 下げない
- 情報を色だけで伝えない

### ダークモード

明るい色を反転させるだけでは成立しない。

- 純黒背景 `#000` は避ける。`#121212`〜`#1a1a1a` 程度に浮かせる（コントラストが強すぎると滲む）
- **ダークモードでは彩度を落とす。** 明るい背景で綺麗な鮮やかな色は、暗い背景で目に刺さる
- 影で高さを表現できないので、**明度で表現する**（手前ほど明るい）
- `<html>` に `color-scheme: dark` を指定する（フォームやスクロールバーの標準UIが追従する）
- `<meta name="theme-color">` を背景色に合わせる

```css
:root { color-scheme: light dark; }
```

## 余白

### 8px グリッド

**基準単位は 8px。** 4px は微調整のみ。
⚠️ デジタル庁デザインシステムも基準単位を 8 CSS px としている。
[出典](https://design.digital.go.jp/dads/foundations/spacing/)（本文照合済）

```
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128
```

Tailwind の既定スケール（`1`=4px, `2`=8px, `4`=16px …）はこれに合致するので、
**Tailwind を使うなら任意の px 値を書かず、既定スケールに乗せる。**
`p-[13px]` のような値が出てきたら、それは設計ミスのサイン。

> デジタル庁の資料は「スタイルガイドで定義される余白スケールは3〜5個程度になることが多い」とし、
> 全トークンの網羅リストは示していない。**必要な数だけ定義すればよい**という立場。
> 上のスケールは Tailwind 既定と実務慣行に基づく（⚠️ 一次資料の記載ではない）。

### 近接の原則 — 余白は「関係」を表す

これが余白設計の本質。装飾ではない。

> **関係の近いものは近く、遠いものは遠く。**

```
見出し
  ↕ 8px      ← 見出しと本文は「近い」
本文テキスト
  ↕ 48px     ← 次のセクションは「遠い」
次の見出し
```

**よくある失敗：見出しの上下の余白が同じ。**
見出しは直後の本文に属する。**上を広く、下を狭く。**

```css
h2 { margin-top: 3rem; margin-bottom: 0.75rem; }
```

### 余白のスケール感

| 距離 | 用途 |
|---|---|
| 4–8px | 要素内部（アイコンとラベルの間、バッジの内側） |
| 12–16px | 関連要素間（ラベルと入力欄、カード内の行間） |
| 24–32px | グループ間（カードとカード、フォームの項目群） |
| 48–96px | セクション間（LPの区切り） |

**LPのセクション間余白はケチらない。** 詰まった LP は安く見える。
一方、**管理画面はセクション間も詰める。** 情報密度が価値だから。
→ 同じ余白ルールを両方に適用しない。これが「混ぜない」の実例。

### 揃える

- 左端を揃える。**中央揃えは短いテキストだけ**（本文の中央揃えは読めない）
- 要素の幅・高さの種類を増やさない
- 角丸は 2–3種類まで（例：小=4px / 中=8px / 大=16px）。用途を固定する
- 影も 2–3段階まで。**影を濃くするより、明度差で浮かせる方が上品**

## レイアウト

- **Flex / Grid を使う。** JS で測って配置しない
- 意図しないスクロールバーを出さない
- 画面いっぱいのレイアウトは `env(safe-area-inset-*)` を考慮する（ノッチ・ホームバー）
- flex の子要素を省略表示したいときは `min-w-0` が必要
  （flex アイテムの既定 `min-width: auto` が truncate を効かなくする）

### コンテナ幅の目安

| 用途 | 幅 |
|---|---|
| 読み物本文 | 640–720px（日本語なら 40em 前後） |
| 一般的なコンテンツ | 1024–1280px |
| 管理画面 | 画面いっぱい（`max-width` なし） |
